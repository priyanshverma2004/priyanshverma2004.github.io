FridgeAI

A full-stack kitchen assistant: photograph a fridge, get an inventory, then plan meals, build a shopping list and ask cooking questions — all grounded in what you actually have and a recipe index.

1. The task

Most meal-planning apps ask you to type what you have. That is the friction: people do not know what is in their fridge, and they will not maintain a list. FridgeAI starts from a photo, builds the inventory for you, and only then plans meals, so the plan is constrained by reality rather than by memory.

The scope is deliberately broad — inventory, expiry tracking, meal planning, shopping lists, a grounded chat — because the interesting engineering is in keeping those features consistent with one source of truth: the inventory table.

The honest framing: the React UI was scaffolded with Lovable. I am not claiming the component library as my own work. The parts I wrote and can defend are the FastAPI backend, the data model, the RAG index, the scan pipeline, and the meal-planning and shopping-list logic.

2. How it is built

FastAPI serves a JWT-authenticated API over PostgreSQL; the React frontend calls it through TanStack Router. Inventory is the central table; meal planning, shopping lists and the chat all read from it.

3. Decisions and trade-offs

Inventory as the single source of truth

Meal plans, shopping lists and the chat all read from the inventory table. That keeps them consistent by construction, at the cost of a slightly heavier read path. The alternative — each feature keeping its own copy — is how these apps drift out of sync.

RAG over a recipe book, not over the internet

The chat is grounded in a FAISS index built from a recipe PDF with sentence-transformers. That keeps answers on-topic and reproducible, and it is honest about what the model knows. It also means the assistant is only as good as that one book.

JWT in the client, no refresh tokens

Access tokens expire after a day and there is no refresh flow. Simple and stateless, but a real product would need refresh tokens and revocation. The hardcoded development secret was removed in cleanup; set SECRET_KEY in .env.

Vision scanning as the entry point

Scanning is the feature that makes the rest usable, so it got the most engineering: two providers (Gemini and Groq), a normalised JSON contract, and validation that the response actually contains items before anything is saved.

The repository includes the FastAPI backend, the React frontend, the ingest script and the committed FAISS index. There is no public deployment: it needs a PostgreSQL database and two API keys, and I would rather link a repository that runs than a demo that does not.

What this does not prove: that the UI is mine — it is scaffolded. That the app is production-ready — it is not: no tests, no CI, hardcoded CORS origins, no refresh tokens, an empty generator.py, and a single commit. Those are open issues, listed below, not hidden.

5. What I'd fix next

  • Tests and CI. There are none. The first priority before calling this a product.
  • Fill in rag/generator.py or delete it — right now the chat route calls Groq directly.
  • Refresh tokens and revocation instead of 24-hour access tokens.
  • Configurable CORS and a real deployment target (Render or Fly.io with a managed Postgres).
  • Replace the Lovable UI with components I own, or at least document which files are generated.
  • Cost and latency logging on the scan and chat paths — vision calls are the expensive part.
