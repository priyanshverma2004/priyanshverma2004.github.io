Email Spam Classifier

5,171 labelled emails. A bag-of-words model, a majority baseline, and a per-class report. The accuracy is 97.1% — the useful part is knowing what that number does and does not cover.

1. The task

Binary text classification: given the subject line and body of an email, decide whether it is ham or spam. It is the canonical first NLP project, which is exactly why it is worth doing carefully. A model can reach a high accuracy here while being useless in the two ways that matter: missing spam, or flagging a real message.

The dataset is a labelled collection of 5,171 emails — 3,672 ham and 1,499 spam. It is Enron-era mail; the vocabulary and the scams are from the early 2000s. That is a limitation of the data, not something a better model can fix.

2. The pipeline

LOADpandas · spam_ham_dataset.csv
→
SPLIT80 / 20 · random_state 42
→
VECTORISECountVectorizer · English stopwords
→
CLASSIFYMultinomial Naive Bayes
→
REPORTaccuracy · per-class P / R / F1

The model is deliberately simple. A bag-of-words representation discards word order and treats every token independently; Naive Bayes assumes those tokens are independent given the class. Both assumptions are false, and both are good enough to set a baseline. The point of keeping the first model simple is that any later gain is measurable against something honest.

One decision worth naming: I reported per-class precision and recall instead of only accuracy. For a spam filter, a false positive (a real email marked as spam) is usually worse than a false negative. A single accuracy number hides that trade-off completely.

So the honest sentence is: the model catches roughly 19 of every 20 spam emails, and mislabels roughly one in fifty genuine emails. Both halves matter. The second half is the one a user would complain about.

4. What the number misses

  • It is one split, one seed. There is no cross-validation here, so 97.1% is a point estimate from 1,035 examples, not a confidence interval.
  • The split is not stratified. It lands close to the overall class balance (71.7% ham in test vs. 71.0% overall), but that is luck, not design.
  • The data is dated. Enron-era subject lines and 2001 scam patterns do not describe modern phishing, business-email compromise, or Unicode obfuscation.
  • Bag-of-words is easy to fool. Word order and negation disappear. “Not free” and “free” are made of different tokens, but a model that has learned “free” as a spam cue will not understand the difference on its own.
  • The threshold is the default. A 0.5 cut-off is not a business decision. For a real filter, the threshold should follow the relative cost of false positives and false negatives.
  • Nothing is deployed. There is no drift monitoring, because there is no service. The notebook is the artifact.

5. What I would fix next

  • Stratify the split and run five-fold cross-validation; report mean and standard deviation instead of one number.
  • Compare CountVectorizer + NB against TF-IDF + logistic regression and a linear SVM. Keep the confusion matrices side by side.
  • Plot a precision–recall curve and pick the threshold from the cost of a false positive, rather than accepting 0.5.
  • Do an error analysis of the false positives. For a spam filter, those are the expensive mistakes.
  • Test on a modern corpus to measure the drift the Enron-era data cannot show.

6. Reproduce it

The notebook and the CSV are both in the repository. From a clean environment:

pip install pandas scikit-learn jupyter
jupyter notebook Email_spam1.ipynb

The notebook uses CountVectorizer(stop_words="english") and MultinomialNB(), with an 80/20 split at random_state=42.
