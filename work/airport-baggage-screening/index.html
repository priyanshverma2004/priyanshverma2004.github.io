Airport X-ray screening

A YOLO26n detector for 12 prohibited-item classes in X-ray baggage images — trained twice, once without augmentation and once with, so the effect of the augmentation is measured instead of assumed.

1. The task

Airport baggage screening is an object-detection problem with an awkward shape: the objects are small, overlapping, and rendered in false colour on a cluttered background. A model that is 90% accurate in the aggregate can still miss the one knife in a bag, and missing one is the failure mode that matters.

This project trains a YOLO26n detector on a 12-class X-ray dataset and asks a specific, measurable question: does augmentation actually help, or does it just add training time? The answer is computed, not assumed — both runs use the same base model, the same data, the same 30 epochs, and the same validation set. Only the augmentation policy differs.

The constraint that shaped everything: no pretrained detector was assumed to be good enough. The baseline run disables every augmentation, so the second run has a fair, measured opponent rather than a strawman.

2. The data

13,728 X-ray images, 12 prohibited-item classes, split 80 / 10 / 10 (10,982 train, 1,373 validation, 1,373 test). Each image carries YOLO-format bounding boxes; annotations were validated for class range, coordinate bounds and box dimensions before training.

3. How it was trained

YOLO26n (2.38 M parameters, 5.3 GFLOPs) was trained twice for 30 epochs at imgsz 640. The baseline disables every augmentation; the second run adds HSV jitter, rotation, translation, scale, shear, horizontal flip, mosaic and mixup. Evaluation uses the same validation set and the same Ultralytics metrics for both runs, so the comparison is like-for-like except where noted in section 5.

Augmentation helped on every metric, and the gain is largest where it matters most for screening: recall, +7.9 points. The classes that improved most are the small, ambiguous ones — but they are also still the weakest, which is the honest headline.

  • Best class: HandCuffs at 0.969 precision / 0.955 recall / 0.981 mAP@50.
  • Weakest: Knife at 0.840 / 0.598 / 0.757 and Lighter at 0.939 / 0.683 / 0.723 — both small, thin objects on a noisy background.
  • The Streamlit app exposes a confidence threshold slider (0.10–0.90) so a screener can trade recall for false alarms without retraining.

5. What it misses

  • Validation metrics, not test metrics. The numbers above are on the 1,373-image validation split. The test split was run for predictions but not scored in this version of the work, so the headline could be optimistic.
  • One confound in the comparison. The baseline used batch 8 and the augmented run batch 4, so the gain is not pure augmentation — a fairer follow-up holds the batch size constant.
  • Single run, no seed sweep. One training run per condition; there is no variance estimate.
  • Small-object weakness. Knife (0.60 recall) and Lighter (0.68) remain the hard cases. The dataset has enough instances of them; the model has not learned them yet.
  • No deployed demo. The Streamlit app needs the trained weights, which are not committed. The repository ships the notebooks and the app, not the model.
  • Dataset not redistributed. The images are not in the repository; reproduce with the layout in data/README.md.
What this does not prove: that the detector is safe to use at a checkpoint. There is no false-positive cost analysis, no adversarial or occluded-bag test, and no comparison against a second architecture. It is a measured improvement on one benchmark, not a deployment case.

6. Reproduce it

Clone the repository, install the dependencies, place the dataset under data/, then run the notebooks in order and the app.
